The whole case in one slide

Retire a distributed system AIPerf never wanted — and share a core with Dynamo

Python AIPerf runs a ~10-service, ZeroMQ, multiprocess control plane that exists only to work around the GIL. Porting to Rust collapses it to one process, unlocks bidirectional code reuse with Dynamo, matches Python's measurements on real runs, and pulls several-fold ahead only where the client — not the inference server — is the limit.
Driver 1 · Strategic
One Rust codebase feeds AIPerf and Dynamo. The Dynamo team asked for it.
Driver 2 · Architecture
One multithreaded process replaces the GIL-era service mesh.
The bonus
Parity on real runs; ~2× Python at the byte-exact ceiling (measured); whole workloads simulated in seconds.

Why — the two drivers that carry the case

Strategic reuse, and deleting accidental complexity

DRIVER 01
Shared core with Dynamo
AIPerf and Dynamo reuse each other's Rust code — bidirectionally. Dynamo maintainers asked for this; the Dynamo mocker was built partly as a stand-in engine for AIPerf. One codebase, two products.
DRIVER 02
One process, not ten services
To use a single machine, Python needs ~10 services, a ZeroMQ bus, proxies, and mmap dataset sharing — almost all of it only to escape the GIL. A single-node Rust run is one thread-per-core process.
Consequence
Headroom: ~45k req/s byte-exact on a 144-core node (~2× Python), using under half its cores; ~61k opt-in.
Consequence
One front-end, three modes: online · mock · offline, over one {transport, clock} seam.
Consequence
Simpler ops & instant cold start: no bus to babysit; native binary ready in ms.
AIPerf · The Case for Rust04
NVIDIA
Where the complexity went

Python distributes to use one box; Rust distributes only to exceed one

PYTHON · MANDATORY, EVERY RUN
A distributed system just to fill one machine
  • ~10 services (controller, workers, records manager, timing, …)
  • ZeroMQ message bus + ZMQ proxies for routing
  • mmap dataset sharing to dodge per-process copies
  • multiprocess service managers to fan out past the GIL — on one host
  • per-service CPU tuning at high load (records-manager starvation > 500k)
RUST · DELIBERATE, OPT-IN
One process by default; cells only for true scale-out
  • Single-node run: one binary, worker-local state, no cross-process bus
  • Shared {transport, clock} seams instead of a service mesh
  • Dataset in-process — no mmap, no serialization hop
  • Cellular multi-node behind a trait boundary — to pass the OS connection ceiling
  • You pay for distribution only when you genuinely outgrow one host
“But aren't we going distributed too, with cellular?” Yes — and that is the distinction, not a contradiction. Python's fan-out is mandatory to use one machine (the GIL forces it). Rust's cellular is opt-in scale-out that engages only past one host's ~15–28k connection ceiling.

The hard questions, answered

“Won't free-threaded (no-GIL) Python make this moot?”

The strongest objection — and it dents one pillar, not the case. Free-threaded CPython is real and maturing, so we meet it directly:
IT DOESN'T MOVE THE MAIN CASE
  • Nothing for Driver 1 — a shared Rust core with Dynamo. No-GIL Python gives zero reuse with a Rust project.
  • Removes serialization, not slowness — CPython's per-request/per-token cost, asyncio, and GC remain; N threads still pay the slow primitive N times.
AND IT ARGUES FOR RUST
  • Collapsing the mesh into one free-threaded process is a rewrite of similar magnitude — that buys data races (parallelism without safety), the exact bug class Rust rejects at compile time.
  • Still maturing (single-thread penalty; consolidating free-threaded C-extension ecosystem); startup, single-binary distribution, and the connection ceiling are unchanged.
Net: no-GIL narrows the complexity argument slightly — and strengthens the safety one. If we rewrite the concurrency model anyway, do it where the concurrency is provably correct.

Why Rust, why now

A · The first call was right
Python was chosen for reach — accessibility and contribution speed. Correct for AIPerf's first generation.
B · The barrier is already broken
Not a forecast — the proof. An AI-assisted, spec-driven effort reproduced a mature Python codebase in Rust, at parity. The port existing is the evidence.
C · Feasibility is not a guess
A working prototype already reaches byte-exact config parity and an indistinguishable live A-B — a de-risked investment, with Python as the reference oracle throughout.
The accessibility reason that favored Python has fallen. AI-assisted, spec-driven development makes Rust approachable to write and review — and the port proves it in this codebase, not in theory.
AIPerf · The Case for Rust09
NVIDIA
We are not alone — industry precedent

vLLM already reached the same conclusion

THEIR FRONTEND · vllm-frontend-rs
1 Rust process ≥ 32 Python API servers
A drop-in, OpenAI-compatible Rust replacement for vLLM's Python FastAPI server — opt-in via VLLM_USE_RUST_FRONTEND=1, now vendored in the main vLLM repo (0.24.0). Default Python saturates at ~19% of Rust throughput, with ~10× worse P50 TTFT.
THEIR CLIENT · vllm-bench
A Rust benchmark client — AIPerf's category
vLLM also ships a high-performance Rust benchmark client for serving endpoints, using the same techniques AIPerf does — sending token-ID arrays to skip server-side tokenization, and caching token-length verification per model+server.
Their motivation is our argument, verbatim. Python was chosen for accessibility and the ML ecosystem — reasonable while GPUs were the bottleneck. As GPUs got faster, the asyncio frontend became a real share of CPU time, and more Python processes “add operational complexity and still hit a ceiling.”
Honest scope: vLLM kept its Python GPU engine and ZMQ seam; AIPerf's runner is already all-Rust on the product path — a step further than vLLM took it.

The ask

Greenlight the Rust port

The case rests on strategic reuse with Dynamo and on retiring the GIL-driven distributed system AIPerf never wanted — replacing mandatory single-host fan-out with one process and opt-in cellular scale-out. Performance is a real but bounded bonus: parity where the server dominates, ~3× at the client ceiling, and any workload simulated in seconds. Because a prototype already demonstrates parity, this is a low-risk investment — not a research bet.
