The whole case in one slide

Simplify AIPerf's multiprocess architecture — and expand shared Rust infrastructure

Python AIPerf utilizes a ~10-service, ZeroMQ multiprocess control plane to scale across the GIL. Porting to Rust collapses it into a single multithreaded process, unlocks code reuse across Dynamo and Velo, matches Python's measurements on real runs, and yields additional throughput headroom when the client — not the inference server — is the limit.

Where the complexity went

Python distributes to use one box; Rust distributes only to exceed one

PYTHON · MULTIPROCESSING
Service coordination for single-node scaling
  • ~12 services + 3 ZMQ proxies (controller, workers, records manager, timing, dataset manager, …)
  • ZeroMQ message bus + steerable ZMQ proxies for routing
  • Dedicated dataset service to dodge per-process copies (~30 MiB overhead)
  • multiprocess service managers to parallelize workloads — on one host
  • per-service CPU tuning at high load (records-manager starvation > 500k)
RUST · MULTITHREADING
One process by default; cells only for true scale-out
  • Single-node run: one binary, worker-local state (Rc<RefCell<_>>, no mutex on the hot path)
  • Three seams, not a mesh — Clock (time), RequestSink+RequestObserver (dispatch), WorkerSink (transport)
  • Dataset in-process via content-addressed SegmentStore — BLAKE3 handles, zero-copy across threads
  • Cellular multi-node behind the cellular feature gate — velo transport for cross-host, or local subprocesses
  • You pay for distributed orchestration only when you outgrow one host

Future-proofing measurements

Ultra-fast silicon exposes Python's timing limits

Current GPU servers often mask client-side overhead, but next-generation custom silicon changes the physics of benchmarking. Rust guarantees the precision required for tomorrow's hardware.
THE PROBLEM: SUB-MILLISECOND ITL
Groq LPUs outpace asyncio & aiohttp
Hardware like the Groq LPU delivers sub-millisecond Inter-Token Latency (ITL). Even with the garbage collector disabled, Python's asyncio loop and aiohttp inherently coalesce packets. When the hardware responds in 0.8ms, a 2ms event-loop coalescing delay corrupts the measurement entirely.
THE SOLUTION: NATIVE TIMING
Deterministic precision
Rust eliminates the interpreter layer between the socket and the timestamp. No GIL contention, no GC pauses, no per-message Python object allocation. The hot path is thread-local (Rc/RefCell, not mutexes), and timing sleeps use Linux timerfd directly via Tokio's IO layer for nanosecond precision. As inference hardware accelerates to microsecond ITL, the benchmarking tool remains an authoritative observer.

The hard questions, answered

“Won't free-threaded (no-GIL) Python make this moot?”

A common consideration that shifts the focus, but preserves the primary benefits. Free-threaded CPython is real and maturing, so we meet it directly:
IT DOESN'T MOVE THE MAIN CASE
  • Nothing for Driver 1 — leveraging shared Rust infrastructure. No-GIL Python gives zero reuse with Dynamo or Velo.
  • Removes serialization, not slowness — CPython's per-request/per-token cost, asyncio packet coalescing, and GC remain.
AND IT ARGUES FOR RUST
  • Removing the GIL without Rust's ownership model leaves shared state to runtime discipline — data races become a testing problem, not a compile-time guarantee. Rust rejects them at the type level.
  • Still maturing (single-thread penalty); startup speed, single-binary distribution, and OS limits are unchanged.

Rollout & Impact

A transparent, drop-in replacement

Replacing a core benchmarking tool cannot disrupt existing pipelines. The Rust port is designed to be invisible to CI/CD systems, while enabling future rich outputs.
ZERO-FRICTION ADOPTION
  • Identical CLI Interface: Existing scripts, Jenkins jobs, and user commands run without modification. The CLI flags parse identically.
  • Single Binary Distribution: Replaces a complex Python environment setup with a single, standalone executable.
  • Future-Ready Outputs: While standard stdout/reports remain identical for parity, the new architecture enables seamless integration of richer, more detailed output formats in the future.
Bottom Line: Teams do not need to rewrite their benchmarks or automation to adopt this.
