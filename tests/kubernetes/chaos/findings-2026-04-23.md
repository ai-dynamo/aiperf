## Scenarios

### Pre-flight bug: server_metrics_manager OOM at 128Mi blocks SystemController

- **Setup:** Applied baseline CR against fresh cluster with operator env defaults from `tests/kubernetes/helpers/operator.py` (`AIPERF_K8S_SERVER_METRICS_MANAGER_MEMORY=128Mi`).
- **Observed:** server-metrics-manager container OOMKilled at ~25s. SystemController log shows `Waiting for configuration: 6/6 (35.0s elapsed). Pending types: {'server_metrics_manager': '0/1'}` — loops forever. CR stuck in `Initializing`.
- **Expected:** Either (a) server_metrics_manager shouldn't be required when no server-metrics endpoint is configured, or (b) SystemController times out and marks CR Failed, or (c) Operator detects container terminated state on non-control-plane container and fails. Currently none of those happen.
- **Verdict:** Interesting / pre-existing bug. `_maybe_recover_terminated_controller` in `src/aiperf/operator/handlers/monitor.py:879` only inspects `Containers.CONTROL_PLANE` terminated state — any other container silently dies without operator noticing.
- **Workaround for continued chaos testing:** bumped `AIPERF_K8S_SERVER_METRICS_MANAGER_MEMORY=256Mi` on the operator Deployment.
- **Bonus observation:** CR delete while stuck in `Initializing` DID complete cleanly (~2s). Finalizer processed, JobSet owner-ref GC reaped the pods. No hang.

### C1 — Delete AIPerfJob mid-ramp

- **Setup:** baseline CR `chaos-baseline` in `aiperf-jobs-master`, profiling phase, 13.9% progress (17913 requests sent, `currentPhase=profiling`, `phase=Running`).
- **Injection:** `kubectl delete aiperfjob chaos-baseline -n aiperf-jobs-master --wait=false` at `07:48:30.246`.
- **Observed:**
  - `07:48:30.319` — kopf `on_delete` handler fires (73 ms after API delete)
  - `07:48:30.320` — operator logs `Deleting AIPerfJob aiperf-jobs-master/chaos-baseline`, patches out finalizer
  - `07:48:30.334` — kopf reports `Deleted, really deleted`
  - CR `GONE` by tick=1 (~80 ms)
  - JobSet `GONE` by tick=1 (owner-ref GC)
  - Pods transitioned to Terminating immediately; **30.80 s** until both pods fully reaped (containers SIGTERM → graceful shutdown grace period)
- **Expected:** `on_delete` → `request_cancellation` latches flag, `close_progress_client` releases session, owner-ref GC handles JobSet. No orphaned resources.
- **Verdict:** **PASS**. Cooperative cancellation path works. Finalizer removal is near-instant; pod cleanup is controlled by container SIGTERM grace.
- **Notes:**
  - No bug, but 30 s pod-termination latency is worth remembering for test-harness timeouts.
  - There's a race the observer didn't catch: if a monitor tick happened to be mid-fetch at the exact delete moment, we wouldn't see it in the logs we captured. The `is_cancellation_requested` check at each await boundary ought to short-circuit it. Worth double-checking by testing during fetch-with-retry backoff — defer to C2.

### C2 — Delete CR during completion handler

- **Setup:** quick CR (50 profiling requests). Monitor log-tail triggered `kubectl delete` at the instant the operator logged `Benchmark complete for aiperf-chaos-quick, fetching results and shutting down controller`.
- **Injection:** `07:50:41.496` (within 26 ms of the trigger line at `07:50:41.470`).
- **Observed (sub-second timeline):**
  - `07:50:41.441` — `monitor_progress` tick claimed completion via `aiperf.nvidia.com/completion-claimed` annotation
  - `07:50:41.470` — "Benchmark complete for ..." log
  - `07:50:41.496` — DELETE call (ours)
  - `07:50:41.538` — "Deleted JobSet aiperf-chaos-quick after results stored"
  - `07:50:41.540` — "Shutdown signal sent to ...: 200"
  - `07:50:41.541` — monitor_progress timer succeeded
  - `07:50:41.542` — status patch `phase=Completed`, all metrics populated
  - `07:50:41.647` — kopf delivers `on_delete` handler (151 ms after our API call) — runs and succeeds immediately, finalizer removed
- **Expected:** kopf per-object handler serialization guarantees `on_delete` waits for the in-flight `monitor_progress` tick to finish. `request_cancellation` then latches the flag, `close_progress_client` releases the session, owner-ref GC handles residual resources. Annotation-based `completion-claimed` means even if a second handler tries to claim, it sees the annotation and skips.
- **Verdict:** **PASS** for the observed timing. The 100 ms completion-handler window finished before kopf delivered `on_delete`. Happy-path serialization is correct.
- **Caveat — race window not hit:** handle_completion on a local-cluster mock with 50 requests is ~100 ms end-to-end. To truly exercise "delete while fetch_results_with_retry is mid-backoff," the fetch has to be blocked (see C9 — kill results sidecar to force retry backoff, then delete CR).
- **Codified as:** covered by the fetch-stuck variant in C9; no separate test needed.

### C3 — Two rapid deletes on same CR

- **Setup:** CR in profiling phase. Two `kubectl delete aiperfjob chaos-baseline --wait=false` calls fired 52 ms apart.
- **Observed:** First delete returned `"chaos-baseline" deleted` at `T+67 ms` (finalizer removed, CR gone). Second delete returned `NotFound` at `T+114 ms`. No operator errors, no double-cancellation events in logs.
- **Expected:** `request_cancellation` (uses `event.set()`) and `close_progress_client` (`dict.pop(key, None)`) are both idempotent. Second delete hits `NotFound` at apiserver layer; operator never sees it.
- **Verdict:** **PASS** (trivially, by design). kopf treats each delete as a one-shot; idempotent cache/flag operations.
- **Codified as:** low-value for pytest since behavior is guaranteed by design. Will include a brief sanity test in chaos suite.

### C4 — Kill operator pod mid-benchmark

- **Setup:** longrun CR (120 s duration) in profiling phase.
- **Injection:** `kubectl delete pod -l app.kubernetes.io/name=aiperf-operator --grace-period=0 --force` at `07:54:33.011`.
- **Observed timeline:**
  - `T+0.183 s` — new operator pod Pending
  - `T+2.4 s` — new operator pod Running (not Ready)
  - `T+13.4 s` — new operator pod Ready (2/2)
  - Throughout — controller + worker pods stayed Running, benchmark uninterrupted
  - `T+98.8 s` — benchmark finished naturally, `phase=Completed`, `completionTime` set
  - Pods terminated cleanly after JobSet delete
- **Expected:** kopf re-lists CRs on startup, resumes `monitor_progress` timer. In-process `_shutdown_sent` cache is empty in the new process, but CR-level `aiperf.nvidia.com/completion-claimed` annotation is NOT present yet (mid-benchmark), so the claim race proceeds normally. Fetch + status patch + shutdown-signal all happen exactly once, driven by the new operator.
- **Verdict:** **PASS**. Operator restart was transparent to the benchmark. Recovery time ≈ 13 s. No double-completion, no orphan resources, no lost events.
- **Bonus finding during setup:** `server_metrics_manager` container emits `Kubernetes pod list failed: 403 Forbidden` (log in `kubectl logs -c server-metrics-manager`) because the in-pod SA (`default` in `aiperf-jobs-master`) lacks pod-list RBAC in `default` namespace. SystemController eventually unblocks and profiling starts, but takes 25-30 s longer than needed and spams logs. Worth a separate bug ticket.

### C5 — Kill operator pod during completion handler

- **Setup:** quick CR (50 req). Race: trigger on `Benchmark complete for ...` log line, fire `kubectl delete pod -l app.kubernetes.io/name=aiperf-operator --grace-period=0 --force`.
- **Injection:** `07:58:13.849` (2 ms after the log line at `07:58:13.835`).
- **Observed:** kopf's completion path on the dying operator finished inside ~30 ms (small mock, small result). CR reached `phase=Completed` with the claim annotation intact before the new operator pod became Ready. Pods terminated normally.
- **Verdict:** **PASS (natural race)** but did NOT reach the interesting window. Same fast-happy-path behaviour as C2 on this mock cluster.

### C5b — Synthetic "orphaned completion claim"

- **Setup:** longrun CR (120 s duration) reached `phase=Running,currentPhase=profiling`. Injected a bogus `aiperf.nvidia.com/completion-claimed` annotation AND force-killed the operator pod simultaneously, simulating "operator crashed between claim patch and `handle_completion`".
- **Observed (very bad):**
  - Operator pod Ready again in ~15 s
  - Every `monitor_progress` tick sees `progress.is_complete=True` (once benchmark duration elapses) but `is_completion_claimed(body)=True` (our synthetic stamp), so it takes the `_shutdown_sent.add(key); return False` fast-path in `_fetch_progress` (`src/aiperf/operator/handlers/monitor.py:1063-1067`). Nothing is fetched, no shutdown is sent.
  - Controller's `_stop_system_controller` hook crashed with a **real code bug** (see below), so even the controller-side `signal_benchmark_complete` annotation is never written. The `on_benchmark_complete` kopf handler is thus also never invoked.
  - Controller container exits with Error; JobSet restarts the controller pod (restartPolicy); it begins a **second** warmup run from scratch while the operator still holds the stale claim. CR status merges live metrics from both runs — `currentPhase` flips back from `profiling` to `warmup`.
  - After 3+ minutes of watching, CR remained `Running/warmup` with `completion-claimed` set, controller in a loop. No progress toward terminal state. Required manual CR delete.
- **Verdict:** **FAIL — real bug exposed.**
- **Automated as:** `tests/kubernetes/chaos/test_chaos_operator_resilience.py::test_c5_orphaned_claim_recovers` marked `xfail(strict=False)` — flips to pass when the bug is fixed.

#### Bug A — stale `get_api` import in `completion_signal.py`

`src/aiperf/kubernetes/completion_signal.py:51` does `from aiperf.kubernetes.client import get_api`. That symbol no longer exists in `aiperf.kubernetes.client` (the module was refactored to expose `k8s_client()` as a contextmanager). Every call to `signal_benchmark_complete()` therefore raises `ImportError`. Controller log confirms:

```
ERROR Error running Hook(func=...SystemController._stop_system_controller...) hook for SystemController:
    cannot import name 'get_api' from 'aiperf.kubernetes.client'
```

This is a **live production bug** — it fires on every benchmark completion (!) but is masked in normal operation because the operator's monitor-loop completion path (via `_poll_controller_progress.get_progress`) is redundant with the annotation signal. The bug only becomes visible when the monitor-loop path is blocked (C5b) or disabled. Also, the `try/except` block in `signal_benchmark_complete` only catches `(ApiException, aiohttp.ClientError, OSError)` — `ImportError` escapes, which is why the stop hook fails rather than silently returning False.

#### Bug B — no self-healing for orphaned `completion-claimed` annotation

Once the annotation is set, every code path that would normally drive the CR to `Completed` short-circuits on it:
- `_poll_controller_progress` (monitor.py:423) → `try_claim_completion` returns False → `close_progress_client` + return True (no handle_completion)
- `_fetch_progress` (monitor.py:1063) → annotation present → add to `_shutdown_sent`, return False
- `_maybe_recover_terminated_controller` (monitor.py:928) → `try_claim_completion` returns False → return False
- `on_benchmark_complete` (lifecycle.py:158) → `try_claim_completion` returns False → return

If the annotation is present but `handle_completion` never actually ran (crash between claim and handle_completion), the CR is stuck forever. There is no timer or reconciliation that detects "claim exists but phase != terminal" and runs the handler from scratch.

**Proposed fix direction:** either (a) make completion idempotent and remove the annotation fast-paths for monitor-detected completion (only `on_benchmark_complete` annotation trigger respects the claim), or (b) add a reconcile step: "if claim set AND phase=Running AND progress.is_complete → re-invoke handle_completion" so the redundant path can finish the job.

### C6 — Kill system-controller container mid-ramp

- **Setup:** longrun CR (120 s duration) in profiling.
- **Injection attempt #1:** `kubectl exec ... -c control-plane -- kill -9 1` at `T+0`. **Did not kill the container** — container kept running for 105 s (likely PID 1 is tini / a shim that ignores SIGKILL on itself, or `kill` in the target container shell is a shell builtin that no-ops on non-existent PID).
- **Natural observation:** at `T+105 s` (when benchmark duration elapsed) the controller container exited with `exitCode=1 / reason=Error` — stemming from the `get_api` stop-hook bug (Bug A in C5b). Within 3 s the operator ran `_maybe_recover_terminated_controller`, fetched results via `fetch_results_with_retry` (sidecar still up), won `try_claim_completion` (no prior stamp this time), and patched `phase=Completed`.
- **Verdict:** **PASS for the salvage path; inconclusive for true controller-kill chaos.** The salvage machinery DOES work when the control-plane container exits — which is the point of this scenario. Re-run with a proper kill (`exec pkill -9 -f aiperf.cli`) would repeat it more precisely; left as TODO in README.
- **Codified as:** not yet — deferred until a reliable kill mechanism is validated (open question: does any container in the pod have `kubectl exec` access to `pkill`? The pod uses a minimal image).
- **Side observation:** every successful completion currently records the controller as `exitCode=1 / reason=Error` because of Bug A. This is visible to anyone running `kubectl describe pod` on a finished benchmark and is cosmetically misleading ("the pod failed!") even though the CR is `Completed`.

## Bugs discovered

1. **Bug A — stale `get_api` import in `src/aiperf/kubernetes/completion_signal.py:51`.** Every benchmark completion's `_stop_system_controller` hook crashes with `ImportError: cannot import name 'get_api' from 'aiperf.kubernetes.client'`. Controller exits with `exitCode=1 / reason=Error` even on success. Silent in production because the operator's monitor-loop completion path is redundant. **Fixed** in this change: switched to `k8s_client()` context manager; updated `tests/unit/kubernetes/test_completion_signal.py` to mock `k8s_client`.
2. **Bug B — no self-healing for orphaned `completion-claimed` annotation.** If the operator crashes between stamping the claim and finishing `handle_completion`, the CR is stuck forever: every subsequent path (`_poll_controller_progress`, `_fetch_progress`, `_maybe_recover_terminated_controller`, `on_benchmark_complete`) short-circuits on the annotation. **NOT fixed yet** — see C5b for proposed directions.
3. **Bug C — `server_metrics_manager` OOMs at the test default 128 Mi** and `SystemController` blocks forever waiting for its registration (`src/aiperf/controller/system_controller.py:735` loop has no timeout when a configured service silently dies). Needs either a config timeout or a container-died reconciliation branch. Chaos test suite bumps the env to `256Mi` as a workaround.
4. **Bug D — `server_metrics_manager` attempts cross-namespace pod discovery without RBAC.** Logs `Kubernetes pod list failed: 403 Forbidden: system:serviceaccount:aiperf-jobs-master:default cannot list pods in default`. Non-fatal but adds ~15-25 s of retry spam to every benchmark start and will break in locked-down RBAC environments.
