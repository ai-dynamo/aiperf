## Bugs and interesting findings

### Bug A — salvage-path regression (C5, C6, C7) — **C5 FIXED; C6/C7 separate bug**

All three scenarios expect the operator's fault-recovery path to drive the CR to `Completed`; all three instead either (a) reach `Failed` (C5) or (b) time out at 240s still showing `currentPhase=None` (C6/C7).

This is the same class of regression. The common factor: a benchmark whose **controller process exited with Error** before the completion handler could fetch results. v1's findings (post-fix) logged Bug B — "no self-healing for orphaned completion-claimed annotation" — as RESOLVED via `_recover_orphaned_completion_claim` in `monitor.py`. The current fresh run re-reveals the symptom.

Reproduction: on a fresh `kind-aiperf-chaos` cluster, run:
```
uv run pytest tests/kubernetes/chaos/test_chaos_operator_resilience.py::test_c5_orphaned_claim_recovers \
  -v -m k8s_slow --k8s-cluster aiperf-chaos --k8s-reuse-cluster --k8s-skip-build --timeout=600
```

#### Root cause (C5, 2026-04-23 PM session)

Initial hypothesis blamed `1df90dc71` (SystemController fail-fast). It is not the proximate cause. The real regression is inside `_recover_orphaned_completion_claim`: it fires unconditionally at the top of every `_monitor_tick` when the `completion-claimed` annotation is present and phase is non-terminal — including ticks where the benchmark is **still running**.

Timeline from operator logs (`kubectl --context kind-aiperf-chaos logs -n aiperf-system -l app.kubernetes.io/name=aiperf-operator`):

- `15:55:30Z` — test stamps `aiperf.nvidia.com/completion-claimed` on a CR in `phase=Running, currentPhase=profiling` with ~90 s of benchmark remaining.
- `15:55:31Z` — test force-kills operator pod.
- `15:55:35Z` — operator restarts, first watcher event for `chaos-c5` fires.
- `15:55:39Z` — `_recover_orphaned_completion_claim` runs; `handle_completion` calls `fetch_results_with_retry`. Controller is alive and mid-profiling; only `gpu_telemetry_export.jsonl` + `inputs.json` + `checkpoints/profile_export_aiperf_partial.json` are on disk (no `profile_export_aiperf.{json,csv}`).
- `15:55:39–15:56:36Z` — `_fetch_with_progress_aware_retry` backs off 2 s → 30 s across 5 stagnation attempts (bytes on disk plateau at 99 185 because the partial checkpoint file barely grows between retries).
- `15:56:36Z` — `results fetch … stalled at 99185 bytes for 5 consecutive attempts — giving up`. `handle_completion` then runs `_set_results_phase_and_condition` with `has_files=False` → `set_phase(Phase.FAILED)`, condition `ResultsFetchFailed`. CR is terminal-Failed with ~55 s of the benchmark still to go.

So the bug is not a missing recovery path; it's an unconditionally-eager recovery path. The fix must gate recovery on positive evidence that the benchmark is actually done.

#### Fix

- `src/aiperf/operator/handlers/monitor.py`:
  - New `_benchmark_appears_complete(api, namespace, jobset_name, key)` helper probes two read-only signals, short-circuiting on the first hit:
    1. Controller `/api/progress` with `is_complete=True` and no `connection_error`.
    2. Control-plane container terminated (reason/exit-code agnostic; the salvage path downstream decides whether results are recoverable).
  - `_monitor_tick`'s orphaned-claim branch now runs `_benchmark_appears_complete` before calling `_recover_orphaned_completion_claim`. When the gate returns False we log at DEBUG and fall through to the normal tick body, letting `_fetch_progress` / `_maybe_recover_terminated_controller` discover completion on a subsequent tick.
  - Docstring on `_recover_orphaned_completion_claim` now requires callers to gate on this helper and references the C5 scenario.
- `tests/unit/operator/test_completion_claim.py::TestMonitorIntegration`:
  - Updated `test_orphaned_claim_triggers_handle_completion_recovery` to mock `_benchmark_appears_complete` → True (asserts recovery still fires when benchmark is done).
  - Added `test_orphaned_claim_deferred_while_benchmark_in_flight` with the gate → False to lock in the "defer while running" behaviour.

### Bug B — H1 test is too strict for helm CRD retention — **FIXED**

`helm uninstall` by design retains CRDs and any CR instances (unless the chart's CRDs were installed via templates with purge policy). H1 asserted zero AIPerfJob CRs post-uninstall and failed because the test job's CR was retained — which is exactly what helm does.

**Fix (`b8afb57ac`):** H1 now asserts the Helm release is un-deployed and actively GCs any leftover AIPerfJob CRs it owns before re-installing. Keeps the genuine "clean re-install" signal without fighting helm semantics.

### Bug C — ToxiproxyInjector fixture scope vs pytest-asyncio event loop (FIXED)

`kubectl` is package-scoped in `tests/kubernetes/conftest.py`, which forces `toxiproxy_injector` to also be at least package-scoped. pytest-asyncio wants the fixture's loop scope to match, which we set (`loop_scope="package"`, commit `65a206d8d`). BUT the previous `ToxiproxyInjector` cached a single `aiohttp.ClientSession` created in the package event loop; when a function-scoped test tried to `await session.get(...)`, aiohttp's timeout context manager raised `RuntimeError: Timeout context manager should be used inside a task`. The loops don't share tasks.

**Fix (Option A — preferred per plan):** redesigned `ToxiproxyInjector` to open a short-lived `aiohttp.ClientSession` inside every REST-API method via `async with`, so the aiohttp timeout context always binds to the calling test's event loop. The kubectl port-forward subprocess stays alive across the package-scoped fixture (only its bound TCP port is reused, not its transport). Module docstring warns future maintainers not to reintroduce a cached session. The `@pytest.mark.xfail(...)` on `test_b3_mock_server_latency_injection` was removed.

Live verification on `kind-aiperf-chaos`: toxiproxy admin reachability probe, `add_proxy(mock-server)`, and `add_toxic(latency=500)` all executed cleanly with no "Timeout context manager" error — the AIPerfJob proceeded through `Pending -> Initializing` with traffic routed via toxiproxy. (The subsequent benchmark-completion assertion failed for an unrelated reason: concurrent test runs on the same cluster clobbered the `aiperf-jobs-master` namespace mid-wait. Honest benchmark-path failure, not a fixture-scope error.)

### XPASS — H4 handles missing JobSet CRD cleanly

The chart's operator Deployment surfaces a clear error condition when its kopf watcher can't find the JobSet CRD, and the AIPerfJob CR creation is blocked cleanly (no orphaned partial state). Was marked xfail as exploratory; keeping marker strict=False so it stays green silently.

### XPASS — C12 invalid endpoint URL rejected

The spec block was expected to be permissive, but the operator / CRD validation rejected `notaschema://nope/v1/chat/completions` within 60s. Likely either Pydantic URL validation in `config.endpoint` or explicit scheme check in `create.py`. Worth understanding which layer rejects, so future chaos tests know whether to probe deeper.

### Worker-label bug found and fixed during this session

Both `ChaosInjector.get_worker_pod_names` and the `_get_worker_pod_uids` helper in `test_chaos_jobset_pods.py` used `replicatedjob-name=worker` (singular), but `jobset_builder.py:458` registers the replicated job as `workers` (plural). Every worker-pod discovery returned empty. Fixed in commit `65a0e9392`. Same-session finding; C6/C7 still failed after the fix due to Bug A.
