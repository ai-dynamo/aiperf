## Bugs and interesting findings

### Bug A — salvage-path regression (C5, C6, C7)

All three scenarios expect the operator's fault-recovery path to drive the CR to `Completed`; all three instead either (a) reach `Failed` (C5) or (b) time out at 240s still showing `currentPhase=None` (C6/C7).

This is the same class of regression. The common factor: a benchmark whose **controller process exited with Error** before the completion handler could fetch results. v1's findings (post-fix) logged Bug B — "no self-healing for orphaned completion-claimed annotation" — as RESOLVED via `_recover_orphaned_completion_claim` in `monitor.py`. The current fresh run re-reveals the symptom.

Hypothesis: commit `1df90dc71` ("fix(controller): SystemController fails fast on sibling-container death") made controller exits more aggressive. When the chaos path kills any in-pod process, the controller now exits with `Error` quickly, and the operator sees a terminal-Error container status before the salvage code path has a chance to fetch results. The `_recover_orphaned_completion_claim` branch may not cover the "controller exited without claim annotation + salvage fetch can't reach live results" case, so the CR lands in `Failed` (or stays `Running` forever on C6/C7 where the controller's post-kill process is replaced by the JobSet).

Reproduction: on a fresh `kind-aiperf-chaos` cluster, run:
```
uv run pytest tests/kubernetes/chaos/test_chaos_operator_resilience.py::test_c5_orphaned_claim_recovers \
  -v -m k8s_slow --k8s-cluster aiperf-chaos --k8s-reuse-cluster --k8s-skip-build --timeout=600
```

Not fixed in this session — out of scope for the expansion.

### Bug B — H1 test is too strict for helm CRD retention

`helm uninstall` by design retains CRDs and any CR instances (unless CRDs are installed via templates, which they are in this chart). H1 asserted zero AIPerfJob CRs post-uninstall and failed because the test job's CR was retained — which is exactly what helm does.

Fix options: (a) update H1 to only assert that the release is gone (`helm status` → not found) and that the operator deployment / namespace are gone, leaving the CRD and CR behind; or (b) have H1 actively `kubectl delete aiperfjob --all` before asserting. Not fixed; the test still surfaces useful signal about a partially-torn-down chart.

### Bug C — ToxiproxyInjector fixture scope vs pytest-asyncio event loop

`kubectl` is package-scoped in `tests/kubernetes/conftest.py`, which forces `toxiproxy_injector` to also be at least package-scoped. pytest-asyncio wants the fixture's loop scope to match, which we set (`loop_scope="package"`, commit `65a206d8d`). BUT `ToxiproxyInjector` holds an `aiohttp.ClientSession` created in the package event loop; when a function-scoped test tries to `await session.get(...)`, aiohttp's timeout context manager raises `RuntimeError: Timeout context manager should be used inside a task`. The loops don't share tasks.

Proper fix requires redesigning `ToxiproxyInjector` to lazily open an aiohttp session per test call (or route admin API calls through `curl` subprocess — slower but avoids the issue entirely). Re-xfailed in commit `d1a04d524` with the full rationale inline.

### XPASS — H4 handles missing JobSet CRD cleanly

The chart's operator Deployment surfaces a clear error condition when its kopf watcher can't find the JobSet CRD, and the AIPerfJob CR creation is blocked cleanly (no orphaned partial state). Was marked xfail as exploratory; keeping marker strict=False so it stays green silently.

### XPASS — C12 invalid endpoint URL rejected

The spec block was expected to be permissive, but the operator / CRD validation rejected `notaschema://nope/v1/chat/completions` within 60s. Likely either Pydantic URL validation in `config.endpoint` or explicit scheme check in `create.py`. Worth understanding which layer rejects, so future chaos tests know whether to probe deeper.

### Worker-label bug found and fixed during this session

Both `ChaosInjector.get_worker_pod_names` and the `_get_worker_pod_uids` helper in `test_chaos_jobset_pods.py` used `replicatedjob-name=worker` (singular), but `jobset_builder.py:458` registers the replicated job as `workers` (plural). Every worker-pod discovery returned empty. Fixed in commit `65a0e9392`. Same-session finding; C6/C7 still failed after the fix due to Bug A.
