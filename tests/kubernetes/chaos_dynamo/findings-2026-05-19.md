# Dynamo Chaos Testing — Findings

Session: 2026-05-19 (scaffold) / 2026-05-19 first-cluster validation pass
Cluster: minikube profile `aiperf` (kubectl context `aiperf`), single RTX 6000 Ada
Branch: `ajc/k8s-post-port` @ HEAD
Operator image: dynamo-operator v0.9.0 (from `nvcr.io/nvidia/ai-dynamo` Helm chart)

## Status

First-cluster validation attempted 2026-05-19. Two surfaced bug fixes
landed (kube-rbac-proxy registry pin; toxiproxy rollout timeout 60s →
300s). The D-series scaffolds themselves have two material gaps that
block end-to-end execution against the v0.9.0 dynamo-operator chart:

1. **apiVersion mismatch.** Scaffolds hardcode
   `apiVersion: nvidia.com/v1beta1`, but the v0.9.0 helm chart installs
   the CRD at `nvidia.com/v1alpha1`. Every DGD-applying test
   (D101, D104, D701, D801, D704) fails fast at `kubectl apply` with
   "no matches for kind DynamoGraphDeployment in version v1beta1".
2. **`gpu_settings` fixture not in chaos_dynamo scope.** `dynamo_config`
   (in `gpu/dynamo/conftest.py`) requires `gpu_settings` (in
   `gpu/conftest.py`), but tests in `chaos_dynamo/` don't transitively
   pull `gpu/conftest.py`. D301 and D704 ERROR at collection-time on
   the missing fixture. D802 is `pytest.skip`-ed before fixture
   resolution so it surfaces cleanly.

## Format

Each scenario:
- **Setup:** what state the dynamo deployment is in when fault is injected
- **Injection:** exact command (or `faults.inject(...)` call)
- **Observed:** what kubectl / logs / `/metrics` showed
- **Expected:** predicted behavior from spec + reading
  `tests/kubernetes/chaos_dynamo/test_chaos_<id>_*.py`
- **Verdict:** Pass / Fail / Interesting / N/A
- **Notes:** follow-ups, bug hypotheses

## Cross-cutting observations

Three blocker classes surfaced on the very first cluster attempt:

1. **Scaffold-vs-installed apiVersion drift** (D101, D104, D701; latent
   in D801, D704). The scaffolds were authored against an in-development
   v1beta1 CRD; the public v0.9.0 chart still ships v1alpha1. Fix:
   either (a) lift `api_version` to a conftest constant resolved from
   `kubectl get crd -o jsonpath='{.spec.versions[*].name}'` once per
   session, or (b) drop the field entirely and let `kubectl apply`
   accept whatever the cluster declares. Option (a) is more robust
   because it lets a single test author against a specific version.
2. **`gpu_settings` fixture scope gap** (D301, D704). The fixture is
   defined in `tests/kubernetes/gpu/conftest.py` but `chaos_dynamo/`
   doesn't transitively import that conftest. The pragmatic fix is to
   move `gpu_settings` (or a slim subset) into `tests/kubernetes/conftest.py`
   so both subpackages see it. Alternative: bring `chaos_dynamo`
   tests under `tests/kubernetes/gpu/` and rename the marker.
3. **Single-GPU host can't host disagg-1gpu mode** (D201, D401, D803,
   D801). `disagg-1gpu` requires both decode and prefill workers to
   land Ready, and `nvidia.com/gpu: 1` schedules only one of them.
   For local minikube validation, an `agg` (single-process) mode would
   let traffic-generation tests run; alternatively the test suite needs
   to detect "GPU count < required" and skip cleanly.

None of these are operator regressions — they are validation-harness
gaps the scaffolds explicitly noted. The two bug fixes shipped this
session (kube-rbac-proxy registry pin; toxiproxy rollout timeout) are
real operator-side issues that block the harness from even reaching
the test bodies, so they had to land first.

### Remaining blockers for Wave-0 closure

The two upstream-version bumps unblocked the **install** path but
exposed a new bucket of harness drift:

1. **v0.9.0 → v1.1.0 CRD shape drift (D104, D701).** Scaffolds bake
   the v0.9.0 `spec.components` list shape and the in-development
   `nvidia.com/v1beta1` group. v1.1.0 ships `spec.services` (map keyed
   by component name, identical to the legacy v1alpha1 alpha shape
   re-promoted) under `nvidia.com/v1alpha1` only. Fix bucket: rewrite
   each scaffolded D-series manifest against v1alpha1 + `spec.services`,
   OR centralize the manifest in a `crd.apply_invalid` helper that
   takes high-level args (`replicas=-1`, `image=<bogus>`) and emits
   whichever schema the live CRD exposes.
2. **`gpu_settings` fixture not visible to `chaos_dynamo/` (D101,
   carryover of last session's D301 / D704).** Promoting the fixture
   to `tests/kubernetes/conftest.py` (or restructuring `chaos_dynamo/`
   under `tests/kubernetes/gpu/`) remains the documented fix; not yet
   landed.
3. **Single-GPU host blocks any "live DGD must serve traffic" path
   (D803, plus D201 / D401 from the prior session).** Independent
   of the version bump. Either swap fixtures to `agg` mode for local
   minikube validation, or move these scenarios behind a
   `requires_multi_gpu` marker that auto-skips on hosts with
   `nvidia.com/gpu < 2`.
4. **Operator deployment-name drift (D101 secondary, would fire after
   the fixture is fixed).** v1.1.0 deployment is
   `dynamo-platform-dynamo-operator-controller-manager`; D101
   `_run_d101_assertion` waits on `deployment/dynamo-operator`.
   Will need a label-selector wait
   (`-l app.kubernetes.io/name=dynamo-operator`) instead of a
   hard-coded deployment name.

Net: the operator install path is now green on v1.1.0; the four
D-series assertions in this pass each surfaced one or more harness-side
fixtures that need to catch up to the v1.x schema before Wave-0 can
close.
