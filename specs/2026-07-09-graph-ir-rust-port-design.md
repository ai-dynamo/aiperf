# Design: Rust port of the AIPerf Graph IR runtime/dataflow plane

- **Date:** 2026-07-09
- **Author:** Anthony Casagrande (with Claude)
- **Status:** Draft for review
- **Scope tag:** `aiperf-graph-ir` (Python source) → fresh standalone Rust crate

## 1. Goal

Port the **runtime/dataflow plane** of AIPerf's Graph IR (`src/aiperf/graph/`) to
Rust as a **pure-logic implementation** with a **standalone evaluator/harness**.
The port reproduces the Python async-dataflow executor's behavior **byte-exactly**
under a deterministic virtual clock, verified against golden fixtures generated by
the in-repo Python executor.

This is a **clean-room, standalone** implementation:

- **No dependency on the existing `aiperf-rs` workspace** and no wiring into its
  (nascent) credit pipeline, worker, or timing crates.
- **No live HTTP / ZMQ / inference server.** The credit issuer is a deterministic
  in-process mock; the port is exercised entirely offline.
- Ships as its own Cargo workspace with its own tests and harness binary.

## 2. What "byte-exact async dataflow" means here

The dataflow executor never emits wire bytes — worker-side materialization does
(out of scope). What the executor deterministically produces is:

1. A **dispatch event stream**: for each fired node, an ordered record of
   `(fired_node_id, all TurnToSend field values, firing-gate wait instants in
   virtual ns, first-token emission)`.
2. A **final channel snapshot** per trace (the `store.snapshot()` result), plus the
   per-firing `snapshot_at_seq` views that LLM nodes read.

**Parity contract (locked):** Given identical `ParsedGraph` + `TraceRecord` inputs,
a deterministic **mock credit issuer** (fixed, replayable return schedule), and an
injected **`SimClock`**, the Rust runtime emits a dispatch event stream **and**
final channel snapshots **byte-identical** to the Python `TraceExecutor`.

Verification: a Python "twin harness" runs the real `TraceExecutor` over a corpus of
graphs with the same mock issuer + `SimClock`, serializing the event stream +
snapshots to canonical JSON. The Rust parity test asserts equality.

## 3. Determinism strategy (the central design element)

Python's byte-exactness rests on two properties, both of which the Rust port must
reproduce:

### 3.1 Single-event-loop happens-before, lock-free

The Python code uses **no locks** anywhere in the hot path. `write_seq` is assigned
by a single monotonic counter in the order writes commit; the executor relies on the
single asyncio loop so a predecessor's `finally`-block writes (`node_finish_wall_us`,
`mark_producer_done`) happen-before a successor's reads. Reduction is made
order-independent by sorting on `(write_seq, writer_node_id)`.

**Rust mirror:** all per-trace state lives behind `Rc<RefCell<…>>` on a **single
thread**. No `Arc`, no `Mutex`, no `Send`/`Sync` requirements on trace state. This is
a faithful translation of the Python structure, not a compromise.

### 3.2 Deterministic scheduling + virtual clock

Firing order is deterministic in Python because:

- `asyncio` dispatches ready callbacks **FIFO** via `call_soon`. Task creation
  (`TaskGroup.create_task`) and event wakes (`asyncio.Event.set()`) enqueue in order.
- The `VirtualClock` (`common/clock.py`) wakes deadline-crossing sleepers in strict
  `(deadline_ns, insertion_id)` **heap order**, and a driver pump advances sim time to
  the earliest parked waiter whenever the loop goes idle.

**Rust mirror — a deterministic single-threaded async runtime whose time layer
adopts ai-dynamo's dynosim DES-clock abstraction.** We do **not** use tokio's
scheduler (its task-readiness order is not guaranteed to match asyncio and would
break `write_seq` assignment). The runtime has two layers:

1. **Virtual-time layer — the dynosim discrete-event-simulation (DES) clock.**
   ai-dynamo's mocker (`lib/mocker/src/replay/offline/{events,runtime_utils}.rs`)
   drives its offline simulation with a `SimulationEvent { at_ms: f64, seq_no: u64,
   kind }` in a min-`BinaryHeap` (reversed `Ord`): `pop()` yields the earliest event,
   **ties broken deterministically by the globally-monotonic `seq_no`** (insertion
   order); a `next_timestamp()` helper takes `min(next_arrival, next_event)` and the
   loop advances `now` to it and drains every event at exactly that instant. This is
   structurally identical to AIPerf's own `VirtualClock` (`(deadline_ns,
   insertion_id)` min-heap + monotonic `advance_to`). We port this DES clock as a
   **generic, reusable** `SimClock` — `SimEvent { at_ns: i64, seq_no: u64 }` (see D2
   for int-ns vs dynosim's f64-ms), a min-`BinaryHeap`, `schedule(at, waker)`,
   `next_event_time()`, `advance_to(now)` waking heap-ordered crossings. The `seq_no`
   tie-break gives the same deterministic same-instant wake order AIPerf's
   `insertion_id` does.

2. **Same-instant task-ordering layer — a cooperative async ready-queue.** dynosim is
   a pure event loop with no async tasks, so it needs nothing here; AIPerf's byte
   parity does. A cooperative executor with a **FIFO ready-queue** (`VecDeque<TaskId>`)
   handles work that happens at the *current* virtual instant with zero time advance —
   task spawn, channel-write wakeups of `await_inputs` waiters, first-token latches.
   Spawning pushes to the tail; a woken waker pushes to the tail; `yield_now`
   re-queues at the tail. This models asyncio's `call_soon` FIFO exactly.

**How they compose (the driver pump):** run the ready-queue to empty (all same-instant
work drains in FIFO order); then ask the `SimClock` for `next_event_time()`, advance to
it, and wake the heap-ordered sleepers whose deadline crossed (which re-fills the
ready-queue); repeat until both are empty. This is exactly dynosim's
`next_timestamp` + advance loop, with the async ready-queue supplying the
same-instant happens-before that AIPerf's single asyncio loop provides.

**dynosim is a pattern source, not a dependency.** Its event/clock API is
`pub(crate)`/`pub(super)` and welded to mocker types (`SimulationEventKind::WorkerCompletion`,
…), so it cannot be imported. We reimplement the generic core cleanly in our crate,
crediting the design.

This runtime is small, fully owned, and the single most important correctness
surface. It is unit-tested independently — DES-heap tie-break order and asyncio-order
golden cases — before the executor is layered on top.

### 3.3 Randomness

`CreditDispatchAdapter._corr_of` mints `x_correlation_id` via `uuid.uuid4().hex`. For
byte-exact parity, **both** the Python twin harness and the Rust port inject a
**deterministic id provider** (a seeded counter or seeded RNG producing identical hex
strings) in place of `uuid4`. The Python side gains a small injection seam
(constructor-injected callable, defaulting to `uuid.uuid4().hex`) used only by the
harness; production behavior is unchanged.

### Supporting types modeled locally (not integrated)

- `TurnToSend` — a local struct mirroring `credit/structs.py`'s graph fields
  (`conversation_id`, `x_correlation_id`, `turn_index`, `num_turns`, `agent_depth`,
  `parent_correlation_id`, `root_correlation_id`, `trace_id`, `node_ordinal`,
  `phase_variant`, `first_token_event`). It is the primary comparison payload; every
  field must match.
- `CatalogContext` / `node_ordinal_for` / `build_catalog_context` — the minimal
  build-time `{trace_id: {node_key: ordinal}}` catalog the adapter needs. Ported from
  `graph_path_catalog.py` (runtime-relevant surface only), or supplied pre-computed in
  the fixture. **Decision D3 below.**
- A `MockCreditIssuer` — deterministic `issue_graph_credit(turn) -> bool` and a
  scripted return/first-token schedule keyed by correlation, driving `adapter.resolve`
  / `adapter.on_first_token` at defined virtual-time instants.

### Out of scope (explicitly excluded)

- `worker_materialize.py`, `dynamic_pool.py` — worker-side content splicing; belong to
  the wire-byte contract, not the dataflow. (`dynamic_pool` is self-contained and can be
  added later if a pool-parity contract is wanted — flagged, not built.)
- `analysis/` (`snapshot.py`, `timeline.py`) — static analyzers, not the runtime.
- `GraphIRReplayStrategy` (2355 lines, `timing/strategies/graph_ir_replay.py`) — the
  *driver* (lanes, recycle, t*, warmup, stop conditions). The harness replaces it for
  parity testing. Porting it byte-exact needs the whole timing/credit pipeline.
- The entire **parse/build plane** (`dataset/graph/` adapters, parser, validator,
  lowering, segment stores). The Rust runtime consumes an already-parsed `ParsedGraph`
  emitted as JSON.

## 5. The standalone evaluator/harness

Two cooperating pieces:

### 5.1 Python twin harness (fixture generator)

A script (lives under `tools/` in the Python repo, or in the Rust workspace calling
the installed `aiperf` package) that:

1. Builds/loads a corpus of `ParsedGraph` + traces — a mix of hand-authored native
   graphs and small real weka/dynamo-derived graphs exercising every dataflow feature
   (see §6 coverage matrix).
2. For each trace, runs the **real** `TraceExecutor` with:
   - an injected `SimClock` + driver pump,
   - a `RecordingMockIssuer` that scripts returns/first-tokens at fixed virtual-ns
     offsets and records every `dispatch(...)` call and the exact `TurnToSend`,
   - the deterministic id provider (§3.3).
3. Serializes to canonical JSON per trace:
   - the input `ParsedGraph`/trace (the Rust input fixture),
   - the mock issuer's return/first-token script (the Rust input fixture),
   - the observed **dispatch event stream** + **final channel snapshot** (the golden
     output).

### 5.2 Rust harness binary + parity test

- A `graph-eval` binary that loads a fixture (`ParsedGraph` + trace + issuer script),
  constructs the Rust `TraceExecutor` + `SimClock` + `MockCreditIssuer` replaying
  the script, runs it, and emits the dispatch event stream + snapshot as canonical
  JSON — usable standalone to *evaluate* any graph, not only for parity.
- A parity test (`cargo test`) that, for every fixture in the golden corpus, runs the
  Rust harness and asserts byte-identical JSON against the Python golden output.
- Canonical JSON = sorted keys, fixed float formatting (integers-as-ns preferred; see
  D2), stable ordering — defined once and shared by both sides.

## 6. Feature coverage matrix (parity corpus must exercise)

- **Reducers:** overwrite single-writer; overwrite conflict (multi-writer → error);
  add_messages append; add_messages id-replacement; messages-typed empty write.
- **Fan-in:** AND-fan-in `count=N`; `count="all"`; orphan on insufficient producers;
  orphan on all-cancelled.
- **Edge delays:** `delay_after_predecessor_us`; `min_start_delay_us` (edge + node);
  `delay_after_predecessor_start_us` (start-anchored); `delay_after_predecessor_first_token_us`
  (post-TTFT) with and without an observed first token; AND-fan-in gate `max`.
- **Absolute start offsets** anchor mode; **compress/ignore edge delays** short-circuit.
- **Scheduling:** OR-fan-in successor walk; start-anchored dispatch-time scheduling;
  cycle guard; mixed-anchor fan-in rejection.
- **Errors:** overflow terminate + downstream orphan-as-clean-stop; `GraphDispatchError`
  mid-conversation containment + sentinel writes (segment-store vs non); issuer refusal
  trace-stop; stickiness error trace-stop; generic exception unwind.
- **Adapter minting:** shaped `{scope}:{turn}` ids; native bare ids; `num_turns`;
  dag identity map (depth + parent corr); first-token sources.
- **Snapshots:** `snapshot_at_seq` global cut for LLM inputs; final `snapshot`.
- **`collapse_leading_start_offsets`** (burst) transform.

## 7. Testing strategy

1. **Runtime unit tests** — the deterministic executor + `SimClock` against
   asyncio-order golden cases (task FIFO, heap wake order, driver-pump idle advance).
2. **Module unit tests** — reducers, channel store (each `await_inputs`/orphan path),
   scheduler (rejection + collapse), adapter minting — ported 1:1 from the Python unit
   tests where they exist, plus new ones for the runtime.
3. **Parity tests** — the §6 corpus, Rust-vs-Python golden JSON, the top-level gate.
4. **Property tests (optional, phase 2)** — random valid graphs, assert Rust==Python
   via a live Python subprocess oracle (proptest).

## 9. Open decisions (defaults chosen; reviewer may veto)

- **D1 — Async runtime:** deterministic single-threaded cooperative executor whose
  virtual-time layer is the **dynosim DES clock** (§3.2), vs tokio
  `current_thread`+`LocalSet`. *Default: the dynosim-DES + cooperative-executor design*
  — tokio cannot guarantee asyncio-matching task order, required for byte-exact
  `write_seq`; the dynosim event-queue gives deterministic virtual-time advance and
  same-instant tie-break for free, and the user directed reusing it.
- **D2 — Time representation in fixtures:** the `SimClock` keys events on **integer ns**
  (AIPerf's `VirtualClock` native unit), *not* dynosim's `f64` ms — this matches the
  Python executor (which sleeps `int(wait_us * 1000)` ns, so the observable
  virtual-time instant is integer) and sidesteps float-ordering/format hazards.
  *Default: compare integer-ns virtual-time instants + integer seq numbers; do not
  compare intermediate float µs.*
- **D3 — Catalog source:** port `build_catalog_context`/`node_ordinal_for` to Rust vs
  emit the resolved `CatalogContext` into the fixture JSON. *Default: emit into the
  fixture* (smaller port surface; the catalog is build-plane-derived and out of the
  runtime's byte-exact concern — the adapter only reads ordinals from it).
- **D4 — `worker_materialize` / `dynamic_pool`:** excluded from the first port.
  *Default: excluded.*
- **D5 — id provider parity seam in Python:** add a constructor-injected
  `id_factory` to `CreditDispatchAdapter` (default `uuid.uuid4().hex`) used only by the
  harness. *Default: yes* — it is the minimal, production-neutral change to the Python
  side required for correlation-id parity.

## 10. Risks

- **R1 (highest):** the deterministic runtime not matching asyncio task order in a
  subtle case (e.g. exception-group unwind ordering in `TaskGroup`, or the interleave
  of an `await_inputs` wake vs a same-tick clock advance). Mitigation: build/lock the
  runtime first with dedicated order-golden tests before the executor lands.
- **R2:** float µs → ns rounding divergence. Mitigation: D2 (integer-ns comparison).
- **R3:** `MessageList` reducer semantics (id-index rebuild on copy) — Rust has no
  deepcopy/pickle path, so the index is simply maintained on the owned `Vec`; ensure
  the reduction output ordering matches. Low risk, covered by §6 tests.
- **R4:** Python source drift during the port (shared active branch). Mitigation:
  pin fixtures to a specific commit; regenerate on rebase.

## 11. Explicitly non-goals

- Performance/throughput parity or optimization (correctness first; the port is not a
  drop-in for the live Python runtime).
- Windows/macOS specifics, ZMQ, HTTP, tokenizers, metrics, exporters.
- Porting the parse/build plane, the timing strategy, or worker materialization.

## Addendum — 2026-07-11

The original standalone/offline-only deliverable shape is superseded by the native
Rust workspace. Graph-IR is now partly realized in `crates/aiperf-graph`, which runs
on tokio `current_thread` runtimes with `LocalSet` and uses the shared `drive_sim` /
`drive_real` runtime split. The graph benchmark also has a live HTTP dispatch path
through `aiperf-transport`; it is no longer solely a deterministic in-process mock
harness.

The byte-exact dataflow and deterministic virtual-clock goals still matter for graph
logic, but new work should preserve the current `SimClock` + `LocalSet` architecture
and the transport-backed benchmark path instead of reintroducing a separate custom
FIFO executor or a detached Cargo workspace.
