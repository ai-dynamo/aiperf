# Design: Rust port of the AIPerf Graph IR runtime/dataflow plane

- **Date:** 2026-07-09
- **Author:** Anthony Casagrande (with Claude)
- **Status:** Built. The runtime/dataflow plane is realized natively in `aiperf_runtime::graph`
  (module of the `aiperf-runtime` crate, `rust/runtime/src/graph/`), running on tokio
  `current_thread` + `LocalSet` over the shared `drive_sim` / `drive_real` split with an
  injected `SimClock`. It has a live HTTP dispatch path through `aiperf_runtime::transport_http`
  and a feature-gated `dynosim` offline path, and is product-reachable only through the
  `aiperf --execute` strict `graph` workload. Native WEKA and `dynamo.request.trace.v1`
  recorded-trace compilers are built in `aiperf_runtime::graph::recorded`.
- **Scope tag:** `aiperf-graph-ir` (Python source) → native `aiperf_runtime::graph` module

## 1. Goal

Port the **runtime/dataflow plane** of AIPerf's Graph IR (`src/aiperf/graph/`) to
Rust as a **pure-logic implementation**. The port reproduces the Python async-dataflow
executor's behavior **byte-exactly** under a deterministic virtual clock, verified
against golden fixtures generated by the in-repo Python executor.

The port lives natively in the `aiperf-runtime` crate as `aiperf_runtime::graph` (`rust/runtime/src/graph/`).
It composes with the rest of the runtime rather than shipping as a detached workspace:

- It shares the `aiperf-runtime` crate's `Clock` seam, `drive_sim` / `drive_real` runtime split,
  and `aiperf_runtime::transport_http` dispatch path.
- It has both a deterministic in-process mock path (byte-exact parity) and a **live HTTP
  dispatch path** through `aiperf_runtime::transport_http`, so it is not solely an offline mock
  harness.
- Its sole product entry point is the `aiperf --execute` strict `graph` workload; there is
  no standalone graph binary and no detached Cargo workspace.

## 2. What "byte-exact async dataflow" means here

The dataflow executor never emits wire bytes — worker-side materialization does. What the
executor deterministically produces is:

1. A **dispatch event stream**: for each fired node, an ordered record of
   `(fired_node_id, all TurnToSend field values, firing-gate wait instants in
   virtual ns, first-token emission)`.
2. A **final channel snapshot** per trace (the `store.snapshot()` result), plus the
   per-firing `snapshot_at_seq` views that LLM nodes read.

**Parity contract (locked):** Given identical `ParsedGraph` + `TraceRecord` inputs,
a deterministic **mock credit issuer** (fixed, replayable return schedule), and an
injected **`SimClock`**, the Rust runtime emits a dispatch event stream **and**
final channel snapshots **byte-identical** to the Python `TraceExecutor`.

Verification: a Python "twin harness" runs the real `TraceExecutor` over a corpus of
graphs with the same mock issuer + `SimClock`, serializing the event stream +
snapshots to canonical JSON. The Rust parity test asserts equality.

## 3. Determinism strategy (the central design element)

Python's byte-exactness rests on two properties, both of which the Rust port reproduces:

### 3.1 Single-event-loop happens-before, lock-free

The Python code uses **no locks** anywhere in the hot path. `write_seq` is assigned
by a single monotonic counter in the order writes commit; the executor relies on the
single asyncio loop so a predecessor's `finally`-block writes (`node_finish_wall_us`,
`mark_producer_done`) happen-before a successor's reads. Reduction is made
order-independent by sorting on `(write_seq, writer_node_id)`.

**Rust mirror:** all per-trace state lives behind `Rc<RefCell<…>>` on a **single
thread**. No `Arc`, no `Mutex`, no `Send`/`Sync` requirements on trace state. This is
a faithful translation of the Python structure, not a compromise, and matches the
thread-per-core `!Send` model the rest of the `aiperf` hot path uses.

### 3.2 Deterministic scheduling + virtual clock

Firing order is deterministic in Python because:

- `asyncio` dispatches ready callbacks **FIFO** via `call_soon`. Task creation
  (`TaskGroup.create_task`) and event wakes (`asyncio.Event.set()`) enqueue in order.
- The `VirtualClock` (`common/clock.py`) wakes deadline-crossing sleepers in strict
  `(deadline_ns, insertion_id)` **heap order**, and a driver pump advances sim time to
  the earliest parked waiter whenever the loop goes idle.

**Rust mirror — tokio `current_thread` + `LocalSet` over the shared `drive_sim` /
`drive_real` runtime split, with an injected `SimClock`.** The runtime runs on a single
`current_thread` tokio runtime with a `LocalSet` for `!Send` `spawn_local` tasks. Time is
supplied through the `Clock` seam, never `tokio::time`:

1. **Virtual-time layer — the dynosim discrete-event-simulation (DES) clock.** The
   `SimClock` is a port of ai-dynamo's mocker offline-replay event queue
   (`lib/mocker/src/replay/offline/{events,runtime_utils}.rs`): a min-`BinaryHeap` of
   `SimEvent { at_ns: i64, seq_no: u64 }` with a globally-monotonic `seq_no` tie-break,
   `next_event_time()`, and `advance_to(now)` waking heap-ordered crossings. This is
   structurally identical to AIPerf's own `VirtualClock` (`(deadline_ns, insertion_id)`
   min-heap + monotonic `advance_to`); the `seq_no` tie-break gives the same
   deterministic same-instant wake order AIPerf's `insertion_id` does. dynosim keys on
   `f64` ms; the `SimClock` keys on integer ns (see D2), matching the Python executor
   which sleeps `int(wait_us * 1000)` ns.

2. **Same-instant task-ordering layer — the `drive_sim` idle pump.** The shared
   `drive_sim` driver polls the `LocalSet` to quiescence (draining all same-instant work
   in ready order), then calls `SimClock::next_event_time()`, `advance_to`s it, wakes the
   heap-ordered sleepers whose deadline crossed (which re-fills the ready set), and
   repeats until both are empty. This is exactly dynosim's `next_timestamp` + advance
   loop, and `drive_real` uses the tokio reactor for wall-clock runs — the same executor,
   selected on `Clock::is_virtual()`.

**dynosim is a pattern source, not a dependency.** Its event/clock API is
`pub(crate)`/`pub(super)` and welded to mocker types, so it cannot be imported; the
generic core is reimplemented cleanly, crediting the design.

Earlier drafts proposed a bespoke single-threaded cooperative FIFO executor as a separate
layer. That was superseded: the `SimClock` + `LocalSet` architecture on `current_thread`
tokio, driven by the shared `drive_sim` idle pump, supplies the same-instant
happens-before that AIPerf's single asyncio loop provides, without a custom scheduler. It
is the single most important correctness surface and is unit-tested independently —
DES-heap tie-break order and asyncio-order golden cases — before the executor is layered
on top.

### 3.3 Randomness

`CreditDispatchAdapter._corr_of` mints `x_correlation_id` via `uuid.uuid4().hex`. For
byte-exact parity, **both** the Python twin harness and the Rust port inject a
**deterministic id provider** (a seeded counter or seeded RNG producing identical hex
strings) in place of `uuid4`. The Python side gains a small injection seam
(constructor-injected callable, defaulting to `uuid.uuid4().hex`) used only by the
harness; production behavior is unchanged.

Content synthesis for recorded traces (§4.1) uses the canonical `aiperf_runtime::rng` substrate —
`RngRoot`/canonical namespaces, BLAKE3 seed derivation, and the crate's PCG64
`RandomGenerator` — not a duplicate Python SHA-256/Mersenne-Twister stream. See §4.1 for
the parity consequence.

### 4.1 Native recorded-trace compilers (`aiperf_runtime::graph::recorded`)

The parse/build plane was originally out of scope, but is now built for the two recorded
graph formats. `aiperf_runtime::graph::recorded` owns strict native compilers for recursive WEKA
trace objects and `dynamo.request.trace.v1` request/tool captures. Python never parses or
lowers either format on the product path — it retains only Config-v2/plugin identity,
public-source coordinates, and authored projection.

- **WEKA** accepts single JSON files, sorted JSON directories, inline rows, and
  runner-resolved remote rows.
- **Dynamo** accepts plain or concatenated-gzip JSONL, numerically ordered segment
  directories, and Dynamo writer prefixes. Its compiler unwraps sink envelopes, skips
  uploader markers, deduplicates repeated records, resolves the first non-self parent
  authority, guards the session forest, selects whole root trees, validates a
  capture-wide block size, and synthesizes virtual negative hashes only when recorded
  replay hashes are absent. Dynamo session identity remains header-borne and is uniquified
  with the complete graph-instance nonce at dispatch.

Both formats normalize into the same recorded-request trait boundary and then run **one**
LCP-trie implementation for content-parent selection, active-union idle-gap warping,
interval-order/fan-in edges, causal dispatch/first-token anchors, frozen message roles,
covered-count reconstruction, theoretical cache counts, and dense segment interning.

Explicit `synthesis.allow_dataset_wrap` reaches online and offline graph admission;
without it an over-concurrent phase cannot silently clone a smaller recorded corpus.

**Parity consequence of the canonical RNG:** content synthesis uses `aiperf_runtime::rng`
(BLAKE3/PCG64), not a Python-duplicate random stream. Consequently structural, timing,
token-count, message-boundary, and request-wire parity are source-grounded; default
synthesized text is reproducible within the native BLAKE3 stream but is **not** claimed
byte-identical to the superseded Python random stream. For equivalent logical traces under
that one canonical stream, the native WEKA and Dynamo routes do produce identical
prompt/response segment bytes and exact HTTP request bodies.

### Supporting types modeled locally

- `TurnToSend` — a local struct mirroring `credit/structs.py`'s graph fields
  (`conversation_id`, `x_correlation_id`, `turn_index`, `num_turns`, `agent_depth`,
  `parent_correlation_id`, `root_correlation_id`, `trace_id`, `node_ordinal`,
  `phase_variant`, `first_token_event`). It is the primary comparison payload; every
  field must match.
- `CatalogContext` / `node_ordinal_for` / `build_catalog_context` — the minimal
  build-time `{trace_id: {node_key: ordinal}}` catalog the adapter needs. Supplied
  pre-computed in the fixture (Decision D3).
- A `MockCreditIssuer` — deterministic `issue_graph_credit(turn) -> bool` and a
  scripted return/first-token schedule keyed by correlation, driving `adapter.resolve`
  / `adapter.on_first_token` at defined virtual-time instants.

### Out of scope (explicitly excluded)

- `worker_materialize.py`, `dynamic_pool.py` — worker-side content splicing; belong to
  the wire-byte contract, not the dataflow. (`dynamic_pool` is self-contained and can be
  added later if a pool-parity contract is wanted — flagged, not built.)
- `analysis/` (`snapshot.py`, `timeline.py`) — static analyzers, not the runtime.
- `GraphIRReplayStrategy` (`timing/strategies/graph_ir_replay.py`) — the *driver* (lanes,
  recycle, t*, warmup, stop conditions). The runner's graph phase runtime and the parity
  harness replace it; porting it byte-exact needs the whole timing/credit pipeline.
- The **linear** parse/build plane (`dataset/graph/` linear adapters/loaders). Native WEKA
  and Dynamo recorded compilers are the exception and are built (§4.1); the linear runtime
  otherwise consumes an already-parsed `ParsedGraph` emitted as JSON.

## 5. Product entry point and parity harness

### 5.1 Product entry — the `aiperf --execute` `graph` workload

The Graph-IR library/runtime behavior above is authoritative for graph logic; its sole
product entry point is owned by `2026-07-11-aiperf-runner-only-execution-surface-design.md`.
The runner defines a strict `graph` workload that pairs with `online_http` through
`drive_real` and feature-gated `dynosim` through `drive_sim_with_source`, using the same
runner registries, endpoint bindings, worker-local metrics, native-v2 report, and
capability handshake as scheduled workloads.

The runner's object-safe graph-input resolver selects `dag_jsonl`, `weka_trace`, or
`dynamo_trace`, strictly decodes the selected authored object once, and hands one
`GraphInputBundle` to the same online-real, online-mock, or feature-gated offline
execution path. Graph is product-reachable only after real `aiperf --execute` subprocess
proofs exist for the advertised backend/workload pair; no standalone graph binary or
Python graph executor is an accepted substitute.

### 5.2 Python twin harness (fixture generator)

For byte-exact parity, a script (using the installed `aiperf` package) builds/loads a
corpus of `ParsedGraph` + traces — hand-authored native graphs plus small real
weka/dynamo-derived graphs exercising every dataflow feature (§6). For each trace it runs
the **real** `TraceExecutor` with an injected `SimClock` + driver pump, a
`RecordingMockIssuer` scripting returns/first-tokens at fixed virtual-ns offsets, and the
deterministic id provider (§3.3), then serializes to canonical JSON: the input
`ParsedGraph`/trace, the mock issuer's return/first-token script, and the observed
**dispatch event stream** + **final channel snapshot** (the golden output).

### 5.3 Rust parity test

A parity test (`cargo test`) loads each fixture, constructs the Rust `TraceExecutor` +
`SimClock` + `MockCreditIssuer` replaying the script, runs it, emits the dispatch event
stream + snapshot as canonical JSON, and asserts byte-identical JSON against the Python
golden output. Canonical JSON = sorted keys, integer-ns time (D2), stable ordering —
defined once and shared by both sides.

## 6. Feature coverage matrix (parity corpus must exercise)

- **Reducers:** overwrite single-writer; overwrite conflict (multi-writer → error);
  add_messages append; add_messages id-replacement; messages-typed empty write.
- **Fan-in:** AND-fan-in `count=N`; `count="all"`; orphan on insufficient producers;
  orphan on all-cancelled.
- **Edge delays:** `delay_after_predecessor_us`; `min_start_delay_us` (edge + node);
  `delay_after_predecessor_start_us` (start-anchored); `delay_after_predecessor_first_token_us`
  (post-TTFT) with and without an observed first token; AND-fan-in gate `max`.
- **Absolute start offsets** anchor mode; **compress/ignore edge delays** short-circuit.
- **Scheduling:** OR-fan-in successor walk; start-anchored dispatch-time scheduling;
  cycle guard; mixed-anchor fan-in rejection.
- **Errors:** overflow terminate + downstream orphan-as-clean-stop; `GraphDispatchError`
  mid-conversation containment + sentinel writes (segment-store vs non); issuer refusal
  trace-stop; stickiness error trace-stop; generic exception unwind.
- **Adapter minting:** shaped `{scope}:{turn}` ids; native bare ids; `num_turns`;
  dag identity map (depth + parent corr); first-token sources.
- **Snapshots:** `snapshot_at_seq` global cut for LLM inputs; final `snapshot`.
- **`collapse_leading_start_offsets`** (burst) transform.
- **Recorded formats:** WEKA and Dynamo cross-adapter segment parity — identical
  prompt/response segment bytes and HTTP request bodies for equivalent logical traces.

## 7. Testing strategy

1. **Runtime unit tests** — the deterministic executor + `SimClock` against
   asyncio-order golden cases (task FIFO, heap wake order, driver-pump idle advance).
2. **Module unit tests** — reducers, channel store (each `await_inputs`/orphan path),
   scheduler (rejection + collapse), adapter minting, and the native WEKA/Dynamo
   compilers — ported 1:1 from Python unit tests where they exist, plus new ones.
3. **Parity tests** — the §6 corpus, Rust-vs-Python golden JSON, plus cross-adapter
   recorded-segment parity.
4. **Runner subprocess tests** — strict `aiperf --execute` proofs for the `graph` workload
   over each recorded input format; these are the product conformance gate.
5. **Property tests (optional)** — random valid graphs, assert Rust==Python via a live
   Python subprocess oracle (proptest).

## 8. Deliverable shape (built)

Graph-IR lives inside the `aiperf-runtime` crate, sharing its `Clock` seam, runtime split, and
transport, rather than as a detached workspace:

```
rust/runtime/src/graph/           # the pure-logic runtime port (aiperf_runtime::graph)
  {model,reducers,runtime,channel_store,channels,scheduler,
   context,placement,executor}.rs   # LLM dispatch + credit-adapter logic folded into executor.rs
  recorded/                      # native WEKA + dynamo_trace compilers (aiperf_runtime::graph::recorded)
  # runtime = current_thread tokio + LocalSet drive_sim/drive_real pump
rust/runtime/src/clock/sim_clock.rs  # shared SimClock = dynosim-style DES event queue (aiperf_runtime::clock)
rust/runtime/src/runner_protocol/  # aiperf-cli v2 execution layer: sole product entry — strict `graph` workload + resolver
tools/gen_fixtures.py            # Python twin-harness fixture generator (parity)
fixtures/corpus/*.json           # Python-emitted inputs + golden outputs
```

## 9. Design decisions (resolved)

- **D1 — Async runtime:** *tokio `current_thread` + `LocalSet`* over the shared
  `drive_sim` / `drive_real` split, with an injected `SimClock` for virtual time. The
  earlier proposal of a bespoke cooperative FIFO executor was **not** adopted; the
  `LocalSet` ready-set driven by the `drive_sim` idle pump supplies the same-instant
  happens-before, and `SimClock`'s `seq_no` tie-break supplies the deterministic
  virtual-time advance. Never `tokio::time` for measurement or firing gates.
- **D2 — Time representation in fixtures:** the `SimClock` keys events on **integer ns**
  (AIPerf's `VirtualClock` native unit), *not* dynosim's `f64` ms — this matches the
  Python executor (which sleeps `int(wait_us * 1000)` ns) and sidesteps
  float-ordering/format hazards. Compare integer-ns virtual-time instants + integer seq
  numbers; do not compare intermediate float µs.
- **D3 — Catalog source:** the resolved `CatalogContext` is **emitted into the fixture
  JSON** rather than re-deriving `build_catalog_context`/`node_ordinal_for` in Rust
  (smaller port surface; the catalog is build-plane-derived and out of the runtime's
  byte-exact concern — the adapter only reads ordinals from it).
- **D4 — `worker_materialize` / `dynamic_pool`:** excluded from the port.
- **D5 — id provider parity seam in Python:** `CreditDispatchAdapter` gains a
  constructor-injected `id_factory` (default `uuid.uuid4().hex`) used only by the harness
  — the minimal, production-neutral change required for correlation-id parity.
- **D6 — Recorded-trace RNG:** content synthesis uses the canonical `aiperf_runtime::rng`
  BLAKE3/PCG64 substrate, following the later RNG design ruling, rather than duplicating
  the Python SHA-256/Mersenne-Twister stream (§4.1). Structural/timing/token-count/
  message-boundary/request-wire parity are source-grounded; synthesized text is
  reproducible within the BLAKE3 stream, not byte-identical to the Python random stream.

## 10. Risks

- **R1 (highest):** the runtime not matching asyncio task order in a subtle case
  (e.g. exception-group unwind ordering in `TaskGroup`, or the interleave of an
  `await_inputs` wake vs a same-tick clock advance). Mitigation: the `SimClock` + driver
  pump is locked with dedicated order-golden tests before the executor lands.
- **R2:** float µs → ns rounding divergence. Mitigation: D2 (integer-ns comparison).
- **R3:** `MessageList` reducer semantics (id-index rebuild on copy) — Rust has no
  deepcopy/pickle path, so the index is simply maintained on the owned `Vec`; the
  reduction output ordering must match. Low risk, covered by §6 tests.
- **R4:** Python source drift during the port (shared active branch). Mitigation:
  pin fixtures to a specific commit; regenerate on rebase.

## 11. Explicitly non-goals

- Performance/throughput parity or optimization (correctness first; the port is not a
  drop-in for the live Python runtime).
- Windows/macOS specifics, ZMQ, HTTP proxy handling, tokenizers, metrics, exporters.
- Porting the linear parse/build plane, the timing strategy, or worker materialization.
  (The native WEKA and Dynamo recorded compilers are the built exception — §4.1.)
